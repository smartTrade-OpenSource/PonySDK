# ADR-0014: FDC3 from Java, through the desktop agent of the page

- Status: Accepted
- Date: 2026-10-26

## Context

FDC3 (FINOS) is how the applications of a trader's desktop talk to each other: a blotter broadcasts the selected
instrument, a chart and a ticket follow it; an application raises an intent (`ViewChart`) that another one handles.
The desktop agent (OpenFin, interop.io, Connectifi, Here, Glue42) puts its API in each application's page as
`window.fdc3`, a `DesktopAgent` of the FDC3 2.x standard, and dispatches `fdc3Ready` once it is there.

A PonySDK screen runs its logic on the server, the agent is in the browser: today a PonySDK application that wants
FDC3 writes its own `PAddOn` and JavaScript. Nothing in PonySDK knows FDC3.

## Decision

1. `com.ponysdk.core.ui.fdc3.Fdc3`, a `PAddOn` of the main window, one per context: `Fdc3.get()`. Its JavaScript,
   `script/fdc3-addon.js`, is in the `ponysdk` jar beside `flexlayout-addon.js`; an application lists it with its
   scripts (`ApplicationConfiguration.setJavascript`). No protocol change, nothing in the terminal: the addon's
   method calls and `sendDataToServer` carry it.
2. The API follows the `DesktopAgent` interface, contexts and results as `JsonObject` / `JsonValue` (FDC3 contexts are
   JSON with a `type`):

   | `DesktopAgent` | `Fdc3` |
   |---|---|
   | `getInfo()`, `getUserChannels()`, `getCurrentChannel()` at start | `getState()` (`WAITING`, `READY`, `UNAVAILABLE`), `addStateListener`, `getInfo()`, `getUserChannels()`, `getCurrentChannel()`, `addChannelListener` |
   | `broadcast(context)` | `broadcast(JsonObject)` |
   | `addContextListener(type, handler)` | `addContextListener(String type, Consumer<JsonObject>)`, null for every type |
   | `raiseIntent(intent, context)`, `getResult()` | `raiseIntent(String intent, JsonObject, Consumer<IntentResult>)`: the app that handled it, its result or the error |
   | `addIntentListener(intent, handler)` | `addIntentListener(String intent, Function<JsonObject, JsonValue>)`: the handler's value is the intent's result |
   | `joinUserChannel(id)`, `leaveCurrentChannel()` | the same |

   Every listener returns its `HandlerRegistration` (ADR-0011) and is called on the context's UI thread. The
   JavaScript listens to the agent once per context type and intent, and stops when the last Java listener goes. A
   call made before the agent is ready waits for it. `Fdc3.instrument(ticker, name)` builds the most common context.
3. The agent is found as the standard says for a page: `window.fdc3`, or the `fdc3Ready` event; none within 5 seconds
   is `UNAVAILABLE`. FDC3 2.2's `getAgent()` for a browser-resident agent, which loads a library from npm, is not part
   of this ADR.
4. The sample shows it without a vendor's agent: `script/fdc3-agent.js`, a demonstration desktop agent for the pages
   of one browser (a `BroadcastChannel`), with three user channels, context listeners, and intents resolved to the
   first application that listens. It sets `window.fdc3` only where no agent did. It is not a product: a real
   desktop provides its own.
5. The mini application: the showcase's FDC3 page broadcasts instruments, follows the channel's context, and handles
   `ViewInstrument`; `fdc3-monitor.html`, a plain JavaScript application of the same browser, follows and broadcasts
   too, and raises `ViewInstrument`. Two showcase windows talk to each other the same way.

## Options considered

- **A terminal object type, as `PHost`.** A protocol type and keys, terminal code in every bundle, for an API that
  only some applications use. The addon is loaded by the applications that list it.
- **Typed context classes** (`Instrument`, `Contact`, `Order`…). The standard has twenty context types and lets an
  application define its own; `JsonObject` takes all of them. One helper for the instrument, the context of nearly
  every trading example.
- **The FINOS `@finos/fdc3` library in the addon.** It wraps `window.fdc3` with the same methods; the addon calls
  `window.fdc3` itself and ships no npm dependency.
- **A server-side bridge to the agent** (a desktop agent's own Java API). Specific to each vendor, and the agent lives
  where the window is: in the browser.

## Verification

- Java: the frames each call writes, the listeners per type and intent (the JavaScript told once, and stopped with the
  last), the state, the intent's result and error, the channel; listeners called on the UI thread.
- Browser, with the demonstration agent: a broadcast from the showcase reaches the monitor, the monitor's reaches the
  showcase, an intent raised by the monitor is handled by the showcase and its result returns; without an agent the
  state is `UNAVAILABLE`. On Chrome, Firefox and WebKit.

## Consequences

- An application lists `script/fdc3-addon.js` and calls `Fdc3.get()`: a page without an agent gets `UNAVAILABLE`, and
  nothing else changes.
- The demonstration agent is the sample's: it is not in the `ponysdk` jar.

## Outcome (2026-10-26)

- `Fdc3` (`ponysdk/src/main/java/com/ponysdk/core/ui/fdc3/Fdc3.java`) and `script/fdc3-addon.js`, 5 968 bytes, 1 756
  gzip, loaded only by the applications that list it; `terminal.js` does not change.
- `Fdc3Test`: 10 tests. Two of them caught the dispatch of an intent to the context listeners (an intent's message
  carries its context): the bug showed first in the browser, as a `NullPointerException` on the server.
- The sample: `script/fdc3-agent.js` (6 670 bytes, 2 216 gzip), the showcase's FDC3 page, `fdc3-monitor.html`.
  `fdc3.spec.js`, 6 scenarios on Chrome, Firefox and WebKit: a broadcast both ways, another channel not hearing it and
  a channel joined giving its context, an intent from the monitor handled in Java with its result back, two showcase
  windows, an intent without an application (`NoAppsFound`), a page without an agent (`UNAVAILABLE`).
