# ADR-0011: One way to listen to a custom event, and the traps of the web component API closed

- Status: Accepted
- Date: 2026-10-26

## Context

An audit of the API a developer touches (2026-10-26) found three ways to listen to an event on neighbouring classes:

| Class | Registration | Removal | Listener receives |
|---|---|---|---|
| `PWidget.addEventListener(name, PEventOptions, Consumer<PEvent>)` (ADR-0003) | `HandlerRegistration` | through it | the fields the options name |
| `PWebComponent.onEvent(name, Consumer<JsonObject>)` | `void` | `removeEventListener(name, listener)`, by identity | the protocol's message, the detail as JSON text under the key `"X"` |
| `PHost.addEventListener(name, Consumer<JsonValue>)`, `addAttributeListener` | `void` | `removeEventListener`, `removeAttributeListener`, by identity | the parsed detail; the attribute's value |

A method reference is a new object at each evaluation, so `host.removeAttributeListener("x", label::setText)` removes
nothing, silently. The classes generated by ADR-0010 wrap the consumer in `onEvent`: their listeners cannot be
removed one by one. `PWebComponent.onClientData` iterates its listeners without a copy: a listener that removes itself
throws `ConcurrentModificationException`.

Other traps of `PWebComponent`, each silent:

- `property(name).offHeap()` or `.stateless()` after a `set` changes the storage without moving the value: `get()`
  returns null and the creation still sends the old value.
- `attr(name, value)` and `getAttr` keep attributes apart from `PWidget.setAttribute` and `getAttribute`:
  `getAttribute` does not see an `attr`. Two methods for one thing.
- `PWidget.addEventListener` on a terminal below protocol 4 registers a listener that never fires; only a warning is
  logged.
- The generator renames a member whose name `PWidget` already has (`title` gives `setTitleProperty`) without saying so;
  `setTitle("x")` compiles and sets the HTML attribute. A method parameter of an object type is generated as `String`
  and reaches the element as a string.

`PWebComponent` and `PHost` are new in 3.0 (not in master nor in 2.10): their API changes without deprecation.

## Decision

1. A custom event, dispatched by an element or by the host page, is listened to with
   `HandlerRegistration addEventListener(String name, Consumer<JsonValue> detail)`, on `PWebComponent` and on `PHost`.
   The listener receives the parsed `detail` (`JsonValue.NULL` without one, a JSON string when the detail is not JSON).
   `PHost.addAttributeListener` returns a `HandlerRegistration` too. A DOM event read by fields stays
   `PWidget.addEventListener(name, PEventOptions, Consumer<PEvent>)`: the two overloads differ by what they deliver,
   the detail or named fields.
2. Removed: `PWebComponent.onEvent`, its `removeEventListener` and `removeAllEventListeners`;
   `PHost.removeEventListener` and `removeAttributeListener`. A registration removes its listener.
3. Listeners are called over a copy of their list: one may remove itself, or another.
4. `PWebComponent.attr`, `removeAttr` and `getAttr` are removed: `setAttribute`, `removeAttribute` and `getAttribute` of
   `PWidget` are the one way, cached and replayed at creation as any widget's.
5. Failing early instead of doing nothing:
   - `PropertyHandle.offHeap()`, `stateless()` and `withPatch()` on a handle that holds a value throw
     `IllegalStateException`: the storage is chosen before the first `set`.
   - `PWidget.addEventListener` on a context whose protocol is below 4 throws `IllegalStateException`.
6. The generator (ADR-0010):
   - `onCountChanged(Consumer<JsonValue>)` returns the `HandlerRegistration`;
   - a method parameter of another type than string, number, boolean or literals is a `JsonValue`: an object or an
     array reaches the element parsed, as the terminal parses array elements that are JSON;
   - an attribute whose type is a union of literals takes the field's enum; a renamed member (`…Property`) is reported
     on standard error by the generator and in the method's Javadoc.

   Getters keep their boxed type (`Double getCount()`): null says the server never set the value, which a primitive
   cannot.

## Consequences

- One form to learn per kind of event; every registration is removed the same way.
- Code written against the removed methods of `PWebComponent` and `PHost` (the sample, the tests) moves to the new
  ones; nothing released used them.
- The frames do not change but for attributes: `setAttribute` is `PWidget`'s update instead of `WC_SET_ATTRIBUTE`;
  the terminal sets the attribute either way.
